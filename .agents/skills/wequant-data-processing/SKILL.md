# wequantのデータ処理クラス

このskillはwequantリポジトリ専用。本文中のコードパスとコマンドはリポジトリルート
基準で扱う。設計規則の正本は
[ARCHITECTURE.md](../../../docs/ARCHITECTURE.md)の「データ処理クラスの設計」とし、
規則を変更する場合は同文書を更新する。

## 調査と設計

- [AGENTS.md](../../../AGENTS.md)と上記の設計規則を読み、依頼された範囲と既存の合意を
  確認する。設計相談なら調査と提案まで、実装依頼なら承認済みの範囲を進める。
  同じ範囲の合意を再度求めない。
- `git status --short`で既存変更を確認し、対象クラス・関連テスト・呼び出し側を読む。
  秘密情報やローカルデータは読まない。Notebookの参照調査が必要な場合はコードセルの
  対象APIの利用に絞り、保存された出力やメタデータを表示・実行しない。
- 次の手掛かりから、必要な部分だけ確認する。既存クラスのコピーを新規設計の根拠に
  せず、現在の挙動と今後の方針を区別する。

| 確認対象 | 手掛かり |
| --- | --- |
| 加工クラスと命名 | `src/wequant/data_processing.py`の対象クラス、同種の操作 |
| 読み込みと対象ファイル | `src/wequant/data_loading.py`、`src/wequant/data_files.py` |
| 主な呼び出し側（今後の方針） | `src/wequant/tasks/`のtask。データ処理クラスを利用するtaskを中心に確認する |
| 既存の呼び出し側（互換性確認） | `src/wequant/graph_processing.py`、`utilities/`、関連Notebook |
| 人工データによる検証例 | `tests/test_data_processing.py`、生成APIは`tests/test_data_processing_construction.py`、取得・更新APIは`tests/test_data_processing_getters.py` |

実装前の提案には、対象クラスと責務、入力・出力、状態変更、必要な他データ、主な変更
ファイル、互換性への影響、検証方法を含める。ソースから分からない列の意味や業務上の
条件は仮定として記録し、結果に影響する不明点を確認する。実データの読み込みを、仕様
確認の代わりに行わない。

## 実装への適用

ARCHITECTURE.mdに従い、DataFrameを受け取る加工の入口、読み込みの境界、メソッドの
状態変更と戻り値を決める。複数データを組み合わせる処理では入力の依存を明示する。
同じ列構成・操作の既存クラスで扱える場合は、ファイルごとにクラスを増やさない。

実装を参照するときは、特に次を確認する。

- ファイルに対応する8クラスの共通の入口は`Class(df)`・`Class(df=df)`と
  `Class.from_file(fp)`・`Class.from_file()`。新規の呼び出しはこの形を使う。
  旧形式は移行期間の互換APIとして残しているため、削除やdf必須化を混ぜない。
- `from_file`は管理対象ファイルの検証を行う。一方、旧`CreditbalancePl(fp=...)`は
  任意パスを読み、dfがあればそれを優先する。入口の移行時にはこの違いを確認する。
- 列名変換を行う6クラスは`_COLUMN_RENAMES`と`_normalize_column_names`を使う。
  変換済み・一部変換済みの入力を受け付け、同じ列の旧名と新名の併存はエラーにする。
  型・必須列の共通規則は未導入。列名の変更に混ぜて追加しない。
- `KessanPl`は初期化時に補正・行除外を行う。列名正規化の繰り返しが安全でも、
  初期化全体を繰り返した結果まで同じになるとは仮定しない。
- 財務指標の取得は`FinancequotePl.get_finance_quotes`、ポートフォリオの取得は
  `PortfolioManager.get_portfolio_as_of_specific_date`を使う。対応する`filter_*`は
  `inplace`を持たず、`self.df`を更新して`None`を返す。
- `with_columns_*`の一部は行も除外する。命名だけで副作用や戻り値を判断しない。
- 同じ加工を`get_*`と`with_columns_*`で使う場合は、DataFrameを受け取って加工済み
  DataFrameを返す非公開処理へ分離する。`get_*`はローカル結果だけを使い、
  `with_columns_*`だけがその結果を`self.df`へ代入する。
- 「最新」の対象単位、日付上限を含むか、並び順、必要な前処理・追加列を確認する。
  日付引数には複数の名前があるため、名称統一を目的に既存引数を変えない。
- コメントや型注釈と実装が一致しない場合や、同名メソッドが複数定義されている場合は、
  実際に有効な定義とテスト・利用箇所を確認する。依頼外の修正を混ぜない。

新規メソッドでは、必要な列・型、返す列・単位、評価日と並び順、nullや空データなど
計算に関係する条件をdocstringに記載する。全クラスの移動・継承導入・既存APIの改名を
作業の前提にせず、依頼された処理を小さな変更で実装する。

## 検証と完了

- 小さな人工DataFrameで期待値を確認する。取得メソッドが`self.df`を変更しないこと、
  更新メソッドの結果と戻り値を、変更に応じて検証する。
- 時系列処理なら異なる銘柄・日付境界・順序、結合ならキー重複など、今回の計算を
  誤らせ得る条件を選ぶ。既存処理の変更では、影響する呼び出し方も確認する。
- 読み込みが必要なテストはモックする。`wq dl-pq`やNotebookを動作確認として実行しない。
  標準のテスト方法はAGENTS.mdに従い、変更に関係する最小限の検証から行う。
- 実装と文書の整合性を確認し、変更・追加・削除したファイル、確認結果、未実施の検証、
  未確認の前提を報告する。
